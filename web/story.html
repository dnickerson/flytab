Built by a pilot.
For the cockpit.

How a conversation about social location-sharing became an AI-powered cockpit running on a neural processing unit at 8,500 feet.

Act I

It Started With HowsAboutYa

The conversation was about location sharing — a social concept called HowsAboutYa. Where are your friends? Where are you? Simple enough. But somewhere in that discussion, a different question surfaced.

Pilots think about location differently. They don't want to know where their friends are. They want to know their exact position, altitude, heading, groundspeed — and whether there's a TFR, a SIGMET, or converging traffic in the way.

"What would a pilot-first situational awareness app look like if you built it from scratch?"

That question didn't have a satisfying answer on the App Store. So it became a project. That project was called FlyWhere.

Act II

FlyWhere: Proof It Could Be Done

The prototype was built to answer one question: can you build a capable moving-map cockpit app entirely in a browser, without a native SDK, without a commercial data subscription?

The answer was yes. Vanilla JavaScript, a Leaflet map, WebSockets to a Stratux ADS-B receiver for GPS and traffic, FIS-B weather painted over sectional charts. No bundler, no framework, no App Store gatekeeping.

The airplane

An experimental RV-9A powered by a Lycoming O-360, built and flown by the same person writing the software. Over a thousand hours logged, instrument rated, IFR current. The kind of pilot who reads AIM footnotes for fun and has opinions about approach briefings.

ForeFlight was fine. But it was someone else's product, on someone else's terms, with someone else's roadmap. That wasn't going to work.

FlyWhere proved the concept. The next question was where to run it.

Act III

The iPad Attempt

The natural move was iPad. It's what every pilot uses. The mounting hardware is everywhere. The display is excellent. The ecosystem is mature.

Safari had other ideas.

Strict mixed-content security rules blocked HTTP connections to the Stratux and the Raspberry Pi engine monitor over the cockpit's local network. WebKit's IndexedDB implementation had its own personality. Touch events behaved differently than the spec suggested. The Capacitor wrapper got the app running — mostly — but it never felt solid. Every gain came with a new constraint.

The app worked. It just never felt like it lived there.

There was also a harder ceiling. Apple's sandbox. Apple's review process. Apple's terms. A cockpit tool built on infrastructure you don't control is a liability, not a platform.

So the search for the right hardware continued.

Act IV

The Right Tablet

The Lenovo Yoga Tab Plus changed the equation immediately. Android meant real HTTP, real WebSocket connections, real filesystem access. The Capacitor wrapper that had wrestled with iOS ran clean on first boot. The Stratux connected. The Pi engine monitor streamed EGT, CHT, RPM, and fuel flow without complaint. The display holds up in direct sunlight.

But there was a detail in the spec sheet that stopped everything and reframed the roadmap.

The detail that changed everything

The Yoga Tab Plus contains a dedicated NPU — a Neural Processing Unit — designed for real-time machine learning inference on-device. No cloud round-trip. No latency. No network dependency.

In a cockpit, those three words matter more than anywhere else.

The question was no longer "where do we run this?" The question became: "what do you build when you have real-time ML inference in the cockpit?"

Act V

The Answer

They built an engine anomaly detector. Not a rules engine with hardcoded limits — a model that learned what normal looks like.

A Conv1D autoencoder was trained on real flight data, across every phase of a typical flight. It learned the normal relationships between all the parameters an engine monitor tracks — not just whether any single value exceeded a limit, but whether the pattern was right.

Under the hood

Architecture: Conv1D(64,5)×3 → Dense(8) → Decoder. An autoencoder that compresses 60 seconds of engine data into 8 numbers, then reconstructs it. When reconstruction error spikes, something changed.

Inputs: RPM, EGT×4, CHT×4, oil temperature, oil pressure, fuel flow, altitude — 13 features, 60-sample rolling window at 1Hz.

Per-phase thresholds: What's normal at cruise is anomalous during runup. The model knows the difference.

  • startup
  • warmup
  • runup
  • takeoff
  • climb
  • cruise
  • descent
  • landing

Deployment: INT8 quantized to 121KB. Routes to the NPU via Android's NNAPI delegate, falling back to GPU then CPU. Inference in under 2ms on the NPU.

"The cockpit that doesn't just display data — it understands it."

A dual-confirmation system guards against false alarms: physics rules catch the obvious emergencies instantly, while the ML layer catches the subtle ones — the slow drift that no threshold would have caught until it was too late.

Today

The app flies.
The NPU infers.
The pilot owns the stack.

FlyTab runs on a Yoga Tab mounted in an RV-9A cockpit, connected over WiFi to a Stratux ADS-B receiver and a Raspberry Pi engine monitor. It draws approach plates, paints special use airspace, tracks fuel state, shows ADS-B traffic, renders FIS-B weather, and monitors the engine in real time with an on-device neural network.

No subscription. No cloud dependency. No one else's roadmap.

Built by one pilot. For every pilot.
