The Bug — Startup Race Condition

App starts → traffic WS connecting, situation WS connecting simultaneously
Situation WS closes first (server hiccup, timeout, or fast rejection) → onclose fires
onclose checks: "is traffic WS open?" — NO, still CONNECTING → reconnect NOT scheduled
Traffic WS opens successfully → _setConnected(true) → app shows "connected"
Situation WS is dead and nobody reschedules it — the only reconnect trigger is situation's own onclose, which already fired and was ignored
Result: no situation data → no GPS → no ownship — for the entire flight

The Code — One Missed Case

stratux-client.js — _connectSituation()
this._situationWs.onclose = () => {
    if (this._trafficWs?.readyState === WebSocket.OPEN) {
        setTimeout(() => reconnect(), 2000);
    }
    // ← if traffic not yet OPEN: silent failure, no reconnect ever
};
When situation closes before traffic opens → reconnect guard blocks → traffic opens later → situation never recovers.

The Fix — 2 Lines in _setConnected(true)

_setConnected(state) {
    // ... existing code ...
    if (state) {
        this._resetStaleTimer();
        // When traffic connects, rescue situation WS if it lost the race
        if (!this._situationWs || this._situationWs.readyState === WebSocket.CLOSED) {
            this._connectSituation();
        }
    }
}

Why ForeFlight Was Unaffected

ForeFlight receives GDL90 UDP broadcast from Stratux on port 4000 — a completely separate protocol from FlyTab's WebSocket connections. The Stratux's /situation WS endpoint can fail while GDL90 continues broadcasting. These share no code path.
