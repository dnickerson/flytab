Altitude Intelligence — Three Features

These are related but independent. Which should we design and build first?

A

Altitude Optimizer (Least Time)

In the settings popup — compute total ETE at each candidate altitude using current winds aloft. Show a comparison table. Tap a row to set that altitude. Uses existing recomputeLegs() and _lastWinds — no new data source.

Medium complexity · Builds on existing infrastructure

B

MEA on Route Pills

Display Minimum Enroute Altitude on each leg pill in the route editor. Needs MEA data from NASR airways bundle — need to verify what's already in the DB. Alerts pilot when planned altitude is below MEA.

Medium complexity · Depends on NASR airway data availability

C

Mixing Height from MOS

Fetch MOS gridded forecast along the route, extract mixing height (convective boundary layer top). Show on the altitude optimizer table so pilot can see which altitudes are above the turbulence zone. New data source — MOS endpoint on flywhere.app proxy with 503 warm-up behavior.

Higher complexity · New data source, new parsing

Recommendation: Start with A (Altitude Optimizer) — it's self-contained, no new data dependencies, and the output table becomes the natural home for C (Mixing Height) once that data is available. B (MEA) is independent and can be designed separately.
