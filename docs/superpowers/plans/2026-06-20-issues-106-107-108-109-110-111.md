### Task 4: Fix EDM Fuel Remaining in `_resolveEdmFuel` (#107)

**Files:**
- Modify: `web/cockpit/fuel-overlay.js` — `_resolveEdmFuel()` method (~line 475)

**Context:**
`_resolveEdmFuel()` tries two sources for the EDM fuel remaining:
1. Live engine panel (fresh within 10s) — works correctly.
2. Last row of the most recent flight CSV via `http://localhost:9090/flights/list`.

**The bug:** `TileServer.handleFlightsList()` returns a JSON array of objects: `[{name: "20260519_KLKR.csv", size_bytes: 4321, modified_ms: 1747689600000}, ...]`. But `fuel-overlay.js` treats the array as plain strings: `files.filter(f => /^\d{8}_/.test(f))`. JavaScript coerces the object to `"[object Object]"` for the regex test, which never matches — so `flightFiles` is always empty and the CSV fallback never runs. This broke when TileServer changed to return metadata objects (introduced May 2026).

**Secondary issue:** The `edm_gal` field in fuel measurement history entries has been `0` since this break, because `_resolveEdmFuel()` always returned `null` from the CSV path and often `null` from the live panel path at preflight time (engine not yet running).

The fix is two-character: use `f.name` for filtering and for building the fetch URL.

### Task 6: Map Pan Performance — Airport Layer Cache (#110)

**Files:**
- Modify: `web/cockpit/vector-map-layers.js` — `_updateAirports()` and constructor

**Context:**
On every `moveend` / `zoomend` (debounced 300ms), `_updateDynamicLayers()` calls `_updateAirports()`, which always calls `this._nasr.getAirportsInBounds(south, west, north, east)`. This is an IndexedDB query, and IDB on Android's WebView is noticeably slow (~100–300ms) for bounding-box range queries over 70k+ airport records. The result: the map lags after every small pan.

**Fix:** Add a viewport buffer cache. Only re-query IDB when the new viewport extends outside the previously-queried bounds by more than a margin. Use a 20% margin (of the viewport diagonal). On zoom change, always re-query (zoom changes what airports are visible via runway-length thresholds).

**New state on `VectorMapLayers`:**
```
_aptBoundsCache: { south, west, north, east, zoom, airports: Airport[] } | null
```

When the new viewport is entirely within `_aptBoundsCache` at the same zoom, re-use `airports` from cache and skip the IDB call. Run the filter/add/remove logic on the cached array.

Invalidate cache (set to `null`) when `_forceAirportRefresh()` is called (filter settings changed).

- [ ] **Step 1: Add `_aptBoundsCache` to the VectorMapLayers constructor**

Find the constructor in `web/cockpit/vector-map-layers.js`. Add after the existing `this._updateTimer = null;` (or similar timer field):

```javascript

```

- [ ] **Step 2: Add a cache helper method `_aptBoundsContains()`**

After the constructor (before `init()`), add:

```javascript
    /** True if the cache covers the requested bounds at the same zoom. */
    _aptBoundsContains(south, west, north, east, zoom) {
        const c = this._aptBoundsCache;
        if (!c || c.zoom !== zoom) return false;
        const latPad = (c.north - c.south) * 0.20;
        const lonPad = (c.east  - c.west)  * 0.20;
        return south >= c.south + latPad && north <= c.north - latPad
            && west  >= c.west  + lonPad  && east  <= c.east  - lonPad;
    }
```

The 20% inward pad means the cache is only used when the viewport is well within the previously-queried area. This ensures newly panned-into airports aren't missing.

Find `_updateAirports(south, west, north, east, zoom, overlays)` (~line 1141). Locate this line:

```

                const latBuf = (north - south) * 0.5;
                const lonBuf = (east  - west)  * 0.5;
                airports = await this._nasr.getAirportsInBounds(
                    south - latBuf, west - lonBuf, north + latBuf, east + lonBuf
                );
                this._aptBoundsCache = { south: south - latBuf, west: west - lonBuf,
                                         north: north + latBuf, east: east + lonBuf,
                                         zoom, airports };
            }
```

The 50% buffer on the IDB query means the cached bounds are 2× the viewport size — so a pan of up to half the viewport width in any direction will hit the cache without a new IDB call.
